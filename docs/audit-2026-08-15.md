# 项目整体设计审计

- 日期: 2026-08-15
- 范围: 全代码走读 (app/ 全部模块 + 前端 + schema), 280 测试全过基线
- 目的: 识别设计不合理/可优化点, 供讨论确定下一步方向

## 一、架构层

### A1. SQLite 连接跨线程共享 (风险)
`routes._build_store()` 用 `check_same_thread=False` 让 Web 请求线程与 worker 线程共享同一连接。注释称"顺序访问下安全", 但 worker 线程与请求处理并发时, 同一连接被多线程使用, 依赖 WAL + busy_timeout 兜底。更稳妥的是**每线程独立连接**或连接池。

### A2. worker 单线程串行 (吞吐瓶颈)
`worker_loop` 单线程串行消费 reply_tasks + tiering_tasks。一个 50 客户的分层任务会阻塞所有回复生成 (虽有"回复优先"缓解, 但分层期间回复仍排队)。LLM 调用是 IO 密集, 单线程无法利用并发。

### A3. 连接创建逻辑分散
`_build_store()` 在 routes / worker / `_extract_profile_sync` 多处各自创建连接, 所有权不统一。

## 二、存储层

### S1. Schema 迁移是 ad-hoc ALTER (脆弱)
`_init_schema()` 里 6+ 个 `ALTER TABLE ... try/except` 硬编码迁移。schema 持续增长 (已 6 次 ALTER), 无版本化迁移 (如 `PRAGMA user_version`)。新列/新表靠手写幂等块, 易漏、难维护。

### S2. 画像 EAV 表 + customers 固定列 双轨 (数据模型割裂)
`profiles` 是 EAV (`customer_id, field, value, source`), 而 `customers` 又有固定列 (`display_name/phone/company/country`)。同一实体的数据分两处存, 搜索走两条路径 (`search_customers` 查固定列, `search_profiles` 查 EAV)。客户卡片要拼所有 profile 字段, 查询别扭。

### S3. 向量键回退丢数据 (Bug)
`_msg_vector_key`: 当 `msg_id` 缺失时回退 `(chatId, day)`, 同一天同会话的多条消息**共用同一向量键互相覆盖**, 向量索引只留每天最后一条。SQLite 表有全部消息, 但向量检索丢数据。

## 三、RAG 管线

### R1. 上下文截断用字符数近似 token
`_compress_and_expand` 用 `context_token_limit*4` 字符数截断, 非真实 token 计数。对 4000 token 限制 = 16000 字符, 中英文 token 密度差异大, 可能超限或浪费。

### R2. 父子块展开实现朴素
父块按 `parent_chunk_id` 查回后直接 append, 无去重/无内容重叠处理, 父块可能很大撑爆上下文。

### R3. 多路召回无路由/去重
`retrieve_multi` 恒跑 4 路, 无查询分类; 结果合并后靠 rerank 去重, 但召回阶段可能重复。

## 四、采集器

### C1. 向量化是同步的 (阻塞事件循环)
`_upsert_one` 里 `self.vector_store.upsert_message_vector` 同步调用 bge-m3 嵌入, 在 async tick 内执行。fast_tick 每 2s 一次, 每条新消息都同步嵌入, 可能阻塞循环。注释写"异步向量化"但实际是同步。

### C2. `_merge_idb_dom` 复杂度高 (最脆弱)
LID/手机号/群聊/发送者名归一逻辑嵌套深 (约 100 行), 是 WhatsApp 变更时最易碎的部分。虽已尽力, 但可读性/可测性差。

## 五、画像/匹配

### P1. 结构化摘要未实现 (路线图 P0 缺口)
`build_chat_summary`/`build_customer_summary` 只是消息文本拼接。每次 LLM 调用 (画像抽取/分层/分析) 都重传原始近期消息, token 昂贵且无结构。路线图"历史对话智能摘要"未落地。

### P2. `confirmed` 字段恒为 0
`match_customer` 返回 `confirmed: False`, 但没有任何代码把它置 True。启发式匹配 (显示名 0.6 置信) 可能误合并同名客户, 却无人工确认机制。

## 六、Web/API

### W1. 状态端点返回 HTML 而非 JSON
`/api/reply/status/{task_id}` 返回渲染后的 HTML 片段, 把 API 与前端渲染耦合, 难测试、难复用。

### W2. 参数解析重复
`_reply_params` 与 `_cleanup_params` 都做 form-or-JSON 解析, 可统一。

### W3. `/api/reply` 与 `/api/reply/regenerate` 高度重复
两个路由几乎相同, 可合并。

## 七、LLM 层

### L1. `generate` 无重试/超时
网络瞬时错误直接失败整个任务, worker 里任务标 failed 需人工重试。

### L2. `max_tokens=1024` 硬编码
长回复/长上下文可能被截断。

## 八、前端

### F1. `app.js` 混合范式难维护
vanilla JS + 多个 IIFE + 内联事件, 客户筛选用正则解析 `data-search` 属性 (`/intent_level=([a-d])/`), 脆弱。

## 已实施修复 (2026-08-15)

### S3: 向量键回退防碰撞
`_msg_vector_key` 无 msg_id 时回退键由 `(chatId, day)` 改为 `(chatId, day, ts)`, 同日不同时间戳的消息不再互相覆盖。测试同步更新。

### C1: 向量化后台线程非阻塞
`_upsert_one` 不再同步调用嵌入模型, 改为把 `(key, text, metadata)` 入队 `_vector_pending`; 新增 `_drain_vectors` 在 executor 线程消费 (与 `_drain_profile_updates` 同构), 嵌入推理不再阻塞采集事件循环。`run()` 每轮调用。

### P1: 历史对话结构化摘要 (路线图 P0)
- 新增 `app/profile/summarizer.py`: 按客户聚合聊天, LLM 结构化输出 overview/意向车型/预算/目标国家/核心顾虑/待跟进事项
- 新增 `customer_summaries` 表 (schema.sql) + `SqliteStore.upsert_customer_summary/get_customer_summary`
- 新增 `POST /customers/{id}/summarize` 路由 + `summary.html` 模板 + chat.html 展示区
- 前端客户详情页展示结构化摘要卡片

### P1 增量设计 (2026-08-15 追加)
- `customer_summaries` 表加 `last_ts` 游标列 (已处理到的最大消息 ts)
- 首次生成: 全量最近 N 条/会话, 游标推进到当前最大消息 ts
- 再次触发: 只取 `ts > last_ts` 的新消息 + 旧摘要一起喂给 LLM 增量合并 (INCREMENTAL_PROMPT), 游标推进
- 无新消息时 no-op, 不覆盖旧摘要
- 新增 `SqliteStore.list_messages_after` / `get_customer_summary_last_ts`

### P1 异步化 + 时间戳 (2026-08-15 二轮)
- 摘要接入 worker: 新增 `summary_tasks` 表 + `_execute_summary_task` (worker 串行消费, 与 reply/tiering 同构)
- `POST /customers/{id}/summarize` 改为创建任务返回轮询片段; 新增 `GET /api/summary/status/{task_id}` 轮询
- 前端 `summary_polling.html` 每 1s 轮询, done 后展示摘要卡片
- 新增 `fmt_ts` Jinja 过滤器, `summary.html` 时间戳格式化为 `YYYY-MM-DD HH:MM`

### S1: Schema 迁移版本化 (2026-08-15 三轮)
- 用 `PRAGMA user_version` 记录 schema 版本, 迁移列表 `MIGRATIONS` 有序 (version → [sql])
- `_init_schema`: 先 `executescript(schema.sql)` 建全表 (幂等), 再从当前 user_version 应用到最新
- 每个 ALTER 幂等 (列已存在忽略), 版本推进到最新
- 新增 `tests/storage/test_migrations.py`: 新库版本、旧库补列、幂等重开、部分迁移
